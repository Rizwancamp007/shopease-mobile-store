What the two lectures actually say

Lecture 21 — HCI in the Software Process (Dix Ch. 6)

The lecture places interactive-system design inside the software life cycle — requirements specification → architectural design → detailed design → coding & unit testing → integration & testing → operation & maintenance (the waterfall sequence). Three ideas from it drive this assignment:

  • Requirements for interactive systems cannot all be fixed at the start. Unlike pure waterfall work, a usable interface has to be built, observed with real users and revised — which is why this solution is a tappable prototype, not a static picture.
  • Validation vs verification. Validation = designing the right product (does it meet the user's real needs?); verification = designing the product right (is it built consistently to spec?). ShopEase was validated against the shopper tasks in the brief (navigate, enter data securely, get feedback, browse efficiently) and verified pattern-by-pattern against Lecture 22's usage rules.
  • The formality gap. There is always a distance between messy real-world shopping and any formal process. Patterns help bridge it: they are field-tested, informal solutions that a formal process alone would not invent.

Lecture 21 also introduces usability engineering — usability testing, heuristic evaluation, cognitive walkthrough, think-aloud protocol, focus groups and questionnaires. The checklist at the end of this page turns those into a small test plan for ShopEase.

Lecture 22 — UI Design Patterns

A pattern is a recurring solution to a common design problem — a standard reference point for the experienced designer. The lecture gives 15 patterns, each with a problem summary and usage rules (“use when… / do not use when…”). ShopEase follows those rules literally: for example, Steps Left is used because checkout has 3 steps (the lecture says don't use it for 1–2 steps), Breadcrumbs appear only on the deep product page (never on the home page), and the Fat Footer is secondary navigation, never the main one.

Typography

Bricolage Grotesque for headings and the logo (friendly, confident — a startup feel), Manrope for all UI text and prices. Scale: 21px screen titles, 16–17px section heads, 13–14px body, 11–12px captions. Nothing essential is set below 11px.

Layout & spacing

Single-column mobile frame, 16px side margins, an 8-point spacing rhythm (8 / 12 / 16 / 24px gaps), cards with 14–16px radius, and every tappable target at least 36 × 36px — Dix's ergonomics point from Assignment 1 applied to thumbs instead of desks. One primary action per screen keeps the visual hierarchy obvious.

How it was built — Lecture 21 applied

  1. Requirements: taken from the lab brief itself — users must navigate easily, enter data securely, receive feedback, and browse products efficiently. Those four tasks became the four screens.
  2. Architectural design: four modules — Home/Browse, Product, Checkout, Account — each owning the patterns that belong to its task.
  3. Detailed design: each pattern matched to a screen using Lecture 22's “use when” rules, and rejected where the rules say not to use it (e.g. no Breadcrumbs on Home).
  4. Prototype & test: built as a working prototype, then walked through task-by-task (a cognitive walkthrough in Lecture 21's terms) to catch dead ends.
  5. Validation & verification: validated — does a first-time shopper reach checkout without help? Verified — does every control behave the way its label promises?

Quick usability test (Lecture 21 methods)

Run a 10-minute think-aloud test with 2–3 classmates and note where they hesitate:

  • Task 1: Find headphones under Rs 10,000 using only the tags.
  • Task 2: Change the headphone colour and add it to the cart.
  • Task 3: Complete checkout — at the payment step, ask “how many steps are left?” (Steps Left is working if they answer instantly).
  • Task 4: Create an account with a weak password, then a strong one — did the meter change their choice?

Record successes, errors and hesitations only — this is a test plan; fill in real results after you run it, don't invent them.
